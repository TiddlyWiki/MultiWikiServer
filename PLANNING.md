## Authentication

The referer header can be changed by fetch on same-origin requests making those checks absolutely useless. We also can't use path restricted cookies, because 
they are path to the resource being requested, not the page requesting the resoruce.

- Session cookie
- Signed page tokens
- Content Security Policy

The signed page token includes the session cookie as AAD (additional authenticated data) without including the value of the session cookie in the token. This prevents the token from being used by a different session.

Each wiki page request is served with a page token. The page token includes, at minimum, the url of the page. The CSP prevents a page from accessing a different page at its wiki endpoint. Instead, every page call from fetch must be made to the recipe endpoint for that page, with the signed token.

The signed token is autogenerated as a client tiddler in the recipe response. For the wiki endpoint, this provides the client code with its token. The recipe endpoint does not need to return the client code, but the exact details are still being decided.

Recipe dynamic tiddlers must be excluded from saving and loading in bags and when detected they must be logged and deleted.

When one page wants access to another page's recipe endpoint, it must request access via a redirect to a known endpoint requesting the permission. If the user accepts, the page is given a second token for the delegated permission.

Only primary permission tokens may request access. Delegated permission tokens may not request additional hops.

For static files we will need a hashmap of urls to the array of urls they may access. This is especially important if the PUT saver is enabled. The PUT saver allows files to save themselves. But we can't use the referer to restrict the saving token, so we would have to use CSP to restrict the page to only save themselves.

Site Options: My static files require the ability to 
- read or write wikis. (`/recipe` endpoints)
- change settings (`/admin` endpoints)
- access external URLs (connect-src, script-src, etc) (https, http)

We could use sec- headers to restrict the signed page tokens from being read via fetch, only sending them in document responses. Admin endpoints are also served with dynamic HTML so inserting a page token is trivial, allowing us to restrict `/admin` routes to only the pages served. They are also served with COOP: noopener-allow-popups.

Static files could have a page token added to the query string via redirect, after verifying the sec-* headers. This query string is used by the put saver for all subsequent requests. The token follows all the same rules and if it's invalid a redirect may remove it.

Set `Referrer-Policy: origin` since the referer may be spoofed and should never be used by the server for anything. 


## Planned headers

```
Referrer-Policy: no-referrer
Cross-Origin-Opener-Policy: noopener-allow-popups
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Cache-Control: private, no-store
Content-Security-Policy: frame-ancestors 'none'
Content-Security-Policy: worker-src blob: data:
```

For **admin and wiki pages**, now that CSP is no longer the primary isolation mechanism, I’d make the model:

- **Initial document navigation:** session cookie + Fetch Metadata check.
- **Document response:** inject the signed page token.
- **Subsequent API calls:** require that page token.
- **Top-level isolation:** `Cross-Origin-Opener-Policy: noopener-allow-popups`.
- **Embedding protection:** `X-Frame-Options: DENY` or a tiny CSP containing only `frame-ancestors 'none'`.
- **Referrer suppression:** `Referrer-Policy: no-referrer`.
- **General hardening:** `X-Content-Type-Options: nosniff`.

So a wiki/admin HTML response could look roughly like:

```http
Cross-Origin-Opener-Policy: noopener-allow-popups
Referrer-Policy: no-referrer
Cache-Control: private, no-store
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Content-Security-Policy: frame-ancestors 'none'
```

Sec-Fetch-Dest: serviceworker
Sec-Fetch-Mode: navigate
Sec-Fetch-Dest: document


Never emit Service-Worker-Allowed that broadens a user-controlled worker's scope.

Content-Disposition: attachment

### Why COOP matters here

`Cross-Origin-Opener-Policy: noopener-allow-popups` is specifically designed to allow **same-origin applications with different trust levels** to sever scripting relationships between top-level documents. MDN even uses the example of two applications sharing an origin where one must not be scriptable by the other. [MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cross-Origin-Opener-Policy?utm_source=chatgpt.com)

So a malicious wiki can't do:

```js
const w = window.open("/admin/users");
```

wait for the admin document to load, and then inspect:

```js
w.document
```

The admin document's COOP causes that relationship to be severed.

### What still needs special treatment

There are a few same-origin facilities that COOP **doesn't** partition:

- `localStorage`
- IndexedDB
- `BroadcastChannel`
- cookies
- service workers

So I would avoid putting secrets or authorization material in origin-wide storage.
