A view is all the copy, docs, titles, etc. This includes options for each field type, like placeholder and select options. This is more of a blocks style layout system. A single block has a state. This persists for the duration of the block. Some blocks need to read or write values.

Each block has its own options. Blocks are composable and can always have children, though what they do with those children varies per block. There is the obvious card and field block. Sidebar block. Those are container blocks and contain most of the UI text. They contain actual fields that fit into them. The fields themselves contain state, the two we've been discussing. The field options define things like select options and placeholdder text, button labels, etc. The field may also supply validation. Ideally the field options should include getter and setter functions for the store values (sync key getters). It should not need the store directly at all.

In `working-layout.ts`, we now have a prototype that recasts the admin definition system as a block-based view model instead of a mixed field-and-group config. The page structure is expressed through composable blocks like page, section, card, sidebar, wrap, and field, with container blocks owning UI copy and composition while fields are limited to behavior-oriented concerns such as driver, value binding, shape, options, and validation. Field configuration is now typed through parallel per-driver maps for options, value shapes, and validation contracts, and fields receive getter/setter bindings instead of direct store access. In practice, that means titles and descriptions have been moved out of field definitions and into wrapper blocks, unresolved config mismatches are represented explicitly as missing-field blocks, and the five admin pages have been reshaped into a layered layout that more closely matches the conceptual separation you described between schema, behavior, and view.
